이 저장소의 정체

README 한 줄이 말하듯 code.google.com/archive/p/todengine의 자동 export본이다. 코드 커밋 47개는 전부 vateran.net이 2009년 3월부터 2011년 11월까지 남겼고, 현 소유자 Stiner의 커밋 3개는 2022년 11월에 README와 LICENSE만 추가한 것이다. 즉 코드는 11년째 정지 상태다.

이름의 TOD는 Tool-Oriented Development다. "엔진을 만들고 나중에 툴을 붙인다"가 아니라, 리플렉션 코어 위에 엔진과 에디터가 처음부터 동시에 얹히는 구조를 지향한다. 이 주장이 실제 코드에서 어떻게 관철되는지가 이 문서의 중심이다.

계보: Nebula Device 2

구조를 조금만 들여다보면 Radon Labs의 Nebula Device 2를 상당히 충실하게 재해석한 설계임이 드러난다. 우연의 일치로 보기 어려운 지문들:

  • Kernel 싱글턴이 타입 생성·경로 조회·모듈 등록을 총괄한다 core/kernel.h:22
  • NOH(Named Object Hierarchy) — 모든 노드가 /sys/server/renderer 같은 파일시스템형 절대 경로를 갖는다. 에디터 소스 파일명이 아예 NOHTree.py, NOHPopupMenu.py다
  • cwn(current working node) 스택 — Nebula의 cwd 개념 그대로 kernel.h:pushCwn/popCwn
  • 메서드 시그니처 문자열 규약 v_setName_s, l_getChildren_v — Nebula nCmdProto의 인코딩과 동일한 발상
  • 모듈 DLL 매크로 DECLARE_MODULE / USING_MODULE / REGISTER_TYPE

다만 베낀 것이 아니라 다시 쓴 코드다. Nebula의 nRoot/nClass 대신 자체 Node/Type을 세우고, 프로퍼티 시스템과 문자열 변환 레이어는 독자적으로 설계했다.

/code/tod/core

리플렉션 코어

이 저장소에서 단 한 부분만 읽어야 한다면 여기다. C++에 리플렉션이 없던 시절, 표준 RTTI만으로는 불가능한 "타입 이름으로 객체를 만들고, 프로퍼티 목록을 순회하고, 문자열로 메서드를 호출하는" 능력을 매크로 + 정적 초기화 + 함수 포인터 테이블로 직접 구축한다. 그리고 그 능력 위에 직렬화·스크립트 바인딩·에디터 UI 세 가지가 전부 자동으로 파생된다.

1. 타입 등록 — 매크로가 심는 정적 인스턴스

클래스 선언부에 DECLARE_CLASS(Node, Object)를, 구현부에 IMPLEMENT_CLASS(Node, Object)를 넣는다. 전자는 static tod::ConcreteType<Node> TYPE; 멤버와 virtual Type* getType()을 클래스에 주입하고, 후자는 그 정적 멤버를 #cls 문자열과 베이스 Type 포인터로 정의한다 core/type.h:110-140.

// 헤더
class Node : public Object {
    DECLARE_CLASS(Node, Object);   // → static ConcreteType<Node> TYPE;
};

// 구현
IMPLEMENT_CLASS(Node, Object);     // → ConcreteType<Node> Node::TYPE("Node", &Object::TYPE);

등록이 main() 이전 정적 초기화 단계에서 끝나므로 별도의 등록 호출부가 없다. 추상/구상 구분은 템플릿 두 개로 처리한다 — ConcreteType<T>::create()는 new T()를 반환하고, AbstractConcreteType<T>::create()는 0을 반환한다 core/type.inl. 덕분에 Renderer 같은 순수 가상 클래스도 타입 트리에는 올라가되 스크립트에서 인스턴스화되지는 않는다.

모듈 초기화 시 REGISTER_TYPE(module, SceneServer) 형태로 Kernel의 타입 테이블에 이름을 등록한다. 저장소 전체에서 38개 타입이 이렇게 올라간다 — Engine 모듈 18개, D3D9Graphics 2개, 나머지는 코어 빌트인이다.

2. 지연 바인딩 — 한 번만, 그리고 되돌릴 수 없게

메서드·프로퍼티 테이블은 타입 등록 시점이 아니라 처음 필요해질 때 채워진다. Type::bindMethod()가 T::bindMethod()를 호출한 뒤 FLAG_BINDEDMETHOD를 세우고, 이후 addMethod()는 그 플래그를 보고 무조건 false를 반환한다 core/type.cc:63-70.

bool Type::addMethod(Method* method) {
    if (hasBindedMethod())     // 바인딩 끝난 타입에는 더 못 넣는다
        return false;
    ...
}

BIND_METHOD 매크로가 함수 안에서 static MethodBinder를 선언하는 구조라 재진입해도 객체가 중복 생성되지 않고, 플래그가 등록 자체를 막는다. 시작 비용을 미루면서 중복 등록을 원천 차단하는 깔끔한 처리다. 대가는 런타임 확장 불가 — 플러그인이 기존 타입에 프로퍼티를 덧붙이는 길이 닫힌다.

3. 메서드 바인딩 — 문자열이 곧 시그니처

가장 특이한 부분이다. 메서드마다 v_setName_s 같은 프로토타입 문자열을 붙이고, Method::setPrototype()이 이 문자열을 파싱해 런타임 인자 슬롯을 미리 할당한다.

타입 코드는 13종이다 core/method.cc:build_paramter:

vvoid (슬롯 없음)ffloattVector3

l가변 리스트 플래그 — 뒤따르는 슬롯을 배열로 취급 (l_getChildren_v)

실제 호출은 자유 함수 썽크가 받는다. 메서드 하나당 static void Node_v_setName_s(Node*, Parameter*) 꼴의 함수를 손으로 쓰고, MethodBinder<T>가 union으로 void(*)(Object*, Parameter*)와 void(*)(T*, Parameter*)를 겹쳐 두어 가상 디스패치 없이 호출한다 core/methodbinder.h:36.

// 썽크 — 인자 언패킹 + 결과 패킹만 담당
static void Node_v_setName_s(Node* self, Parameter* param) {
    self->setName(param->in()->get<String>(0));
}

void Node::bindMethod() {
    BIND_METHOD(v_setName_s, Node_v_setName_s);
    BIND_METHOD(l_getChildren_v, Node_l_getChildren_v);
    ...
}

저장소 전체에서 *_method.cc 파일 17개에 썽크 함수 63개가 들어 있고, BIND_METHOD 호출은 86회다. 코어 코드의 무시 못 할 지분이 이 기계적 접착제다.

이 설계가 지불하는 값

프로토타입 문자열과 썽크 시그니처는 컴파일러가 대조해 주지 않는다. v_setName_s라 써 놓고 썽크에서 get<int>(0)을 하면 조용히 잘못된 메모리를 읽는다. 오타 하나가 링크는 통과하고 런타임에 터진다. C++11의 가변 템플릿이 있었다면 bind(&Node::setName) 한 줄로 끝나면서 타입 검증까지 받을 수 있었을 부분이다 — 2009년이라는 시점의 한계다.

4. 프로퍼티 바인딩 — 멤버 함수 포인터 쌍

메서드와 달리 프로퍼티는 훨씬 현대적이다. SimplePropertyBinder<TYPE, PROPERTY_TYPE>이 세터/게터 멤버 함수 포인터를 직접 들고 있어 문자열 파싱이 없다 core/simplepropertybinder.h.

void TransformNode::bindProperty() {
    BIND_PROPERTY(bool, active,  &setActive,  &isActive);
    BIND_PROPERTY(bool, visible, &setVisible, &isVisible);
}

// 세터에 0을 주면 읽기 전용 — 직렬화에서 자동 제외된다
BIND_PROPERTY(int, rppass_index, 0, &getRpPassIndex);

읽기 전용 표현이 특히 경제적이다. 세터 자리에 0을 넣으면 isReadOnly()가 참이 되고, XmlSerializer는 이런 프로퍼티를 건너뛰며 에디터는 편집기를 잠근다 — 별도 플래그 없이 한 인자로 세 곳의 동작이 결정된다. 프로퍼티는 저장소 전체에 56개 등록돼 있으며, ContainerProperty·CompositeProperty·EnumProperty·StructProperty로 중첩·열거형·구조체까지 확장된다.

5. 문자열 변환 레이어 — 확장 지점

리플렉션이 실제로 쓸모 있으려면 Vector3를 "0.000 6.000 6.000"으로 바꾸고 되돌리는 층이 필요하다. Property::toString()은 자기가 변환하지 않고 ToString 싱글턴에 위임하며, 이 싱글턴은 hash_map<type_id, StringConverter*>로 변환기를 찾는다 core/property.cc:9, core/tostring.h:32.

코어가 12개(bool·int·int64·float·double·String·Name·Uri·Vector3·Color 등)를 기본 등록하고, 모듈이 자기 타입의 변환기를 런타임에 추가할 수 있다. Engine 모듈이 초기화 때 FormatStringConverter를 꽂는 것이 그 예다 engine/main.cc:60.

void initialize_Engine(Module* module) {
    ...
    static FormatStringConverter format_sc;
    ToString::instance()->addConverter(&format_sc);   // 코어 수정 없이 타입 추가
}

바인딩 테이블은 잠겨 있지만 변환 테이블은 열려 있다. 코어를 건드리지 않고 새 프로퍼티 타입을 도입하는 유일한 통로이며, 설계에서 가장 잘 뚫어 놓은 구멍이다.

치명적 — x64 이식을 원천 차단

type_id가 typedef int인데, 값을 reinterpret_cast<int>(typeid(T).name())로 만든다 core/typeid.h:22, core/primitivetype.h:45. 64비트에서 포인터를 int로 캐스팅하는 것은 MSVC에서 컴파일 에러(C2440)다. 이 한 줄이 전체 리플렉션 시스템을 x86에 못박는다. 되살리기 작업에서 가장 먼저 손대야 할 지점이고, 다행히 수정은 간단하다 — uintptr_t로 바꾸거나 타입별 정적 카운터로 교체하면 된다.

6. 세 소비자가 테이블을 쓰는 법

직렬화 — 세대 순서를 뒤집는다

XmlSerializer::serialize_properties()는 타입 체인을 std::stack에 밀어 넣은 뒤 꺼내며 순회한다. 즉 베이스 → 파생 순서로 프로퍼티를 쓴다 core/xmlserializer.cc:212-238. 덕분에 저장된 XML에서 공통 속성이 앞에 오고, 복원 시 부모 클래스 상태가 먼저 세팅된다. 실제 산출물이 data/test/test.xml이다:

<TerrainNode heightmap_uri="managed://texture#hmap5x5_tile.png"
             terrain_size="33" uv_repeat="16"
             shader_uri="managed://shader#terrain.fx" technique="Terrain"
             scaling="1.000 0.500 1.000" name="terrain" />

속성 이름이 전부 BIND_PROPERTY에 적힌 이름 그대로다. 씬 포맷을 따로 정의한 파일이 저장소에 없다 — 포맷이 곧 리플렉션 테이블이다.

스크립트 — __getattr__ 한 곳에서 갈린다

Python 브리지의 핵심은 함수 하나다. TodObject_getattro()가 이름으로 먼저 메서드를 찾고, 없으면 프로퍼티를 찾는다 todpython/todpython_object.cc:26-51.

PyObject* TodObject_getattro(TodObject* self, PyObject* name) {
    Type* type = self->object_->getType();
    Method* method = type->findMethod(attr_name);
    if (method) { self->method_ = method; return self; }  // 호출 가능 객체로
    Property* prop = type->findProperty(attr_name);
    if (prop) return build_property_to_pyobject(...);        // 값으로
}

메서드일 때 자기 자신을 반환하고 tp_call에서 invoke_method를 태우는 트릭 덕분에, 바인딩 코드가 클래스별로 하나도 없다. node.setName("terrain")이든 node.terrain_size든 전부 이 한 함수를 지난다. Lua 쪽도 동형이다.

에디터 — 세대별로 그룹을 만든다

PropertyGrid.setObject()는 getGenerations()로 상속 체인의 타입 이름 목록을 받고, 각 타입의 프로퍼티만 뽑아 그룹 헤더를 만든다 tool/lib/PropertyGrid.py:553-563.

for type_name in object.getGenerations():
    prop_names = object.getPropertyNames(type_name)
    group = self.addGroup(type_name)                # "TransformNode" 같은 접이식 그룹
    for prop_name in prop_names:
        name, value, ptype, readonly = object.getProperty(prop_name)
        group.addProperty(object, name, value, ptype, readonly)

편집기 위젯은 getTypeKeyword()가 돌려준 문자열('b', 's', 'vector3', 'uri')로 결정된다. 앱 시작 시 addPropertyValueEditorType('property vector3 editor', 'vector3', PropertyItemValueVector3)로 등록해 두는 방식이라 tool/TodEditor.py:24-27, 새 프로퍼티 타입이 생기면 Python 쪽에 한 줄 더하면 끝난다.

정리: 이 코어가 잘한 것과 못한 것

제대로 작동하는 판단

  • 선언 → 정적 등록으로 등록 코드가 아예 없다
  • 읽기 전용을 세터 자리 0 하나로 표현 — 세 소비자가 같은 신호를 읽는다
  • 변환기 테이블만 런타임 개방 — 확장 지점이 정확히 한 곳
  • 씬 포맷을 따로 정의하지 않는다. 테이블이 곧 스키마
  • 스크립트 바인딩 코드가 클래스당 0줄

지금 갚아야 할 값

  • type_id 포인터 절단 — x64 컴파일 자체가 막힌다
  • 프로토타입 문자열이 무검증. 썽크 63개가 전부 수동 대조 대상
  • 바인딩 후 잠금 → 플러그인의 런타임 타입 확장 불가
  • findMethod가 상속 체인 선형 탐색 (깊이만큼 map 조회)
  • hash_map이 stdext/__gnu_cxx 확장에 묶여 있다

씬그래프와 RenderPath

노드 계층은 SceneNode → TransformNode → AbstractShaderNode → ShaderNode → ShapeNode → MeshNode / TerrainNode / TreeNode / XFileNode로 이어지며, 카메라는 ShaderNode에서 갈라져 나온다. 프레임마다 SceneServer가 그룹을 수집하고 splitNodes → validateNodeResources → sortNodes를 거쳐 64개 버킷으로 정렬한 뒤 렌더한다 engine/sceneserver.h:37-45.

렌더 파이프라인은 코드가 아니라 노드 트리로 기술된다. RenderPath → RpSection → RpPass → RpRenderTarget / RpShader 계층이 그것이며, HDR·블룸 같은 포스트프로세싱을 C++ 수정 없이 구성하려는 의도다. 실제로 data/shader/에 hdr.fx, bloom.fx, terrain.fx, character.fx가 들어 있다. RenderPath 자체가 Node이므로 에디터의 PropertyGrid로 렌더 패스를 편집할 수 있다 — 리플렉션 코어가 만든 배당금이다.

TOD 패러다임의 실체

프로젝트 이름이 걸린 부분이다. wxPython 에디터가 todpython 확장 모듈로 엔진을 임포트한다. 엔진이 툴을 띄우는 게 아니라 툴이 엔진을 라이브러리로 쓴다.

가장 특징적인 것은 메인 루프가 뒤집혀 있다는 점이다. wx가 루프를 돌고 엔진을 틱시키는 게 아니라, 엔진의 TriggerServer::trigger()가 루프를 돌고 그 안에서 wx 이벤트를 펌프한다 tool/TodEditor.py:41-47:

def MainLoop(self):
    event_loop = wx.EventLoop()
    wx.EventLoop.SetActive(event_loop)
    while self.triggerServer.trigger():      # 엔진이 시간을 소유한다
        self.update(event_loop)                # wx는 그 안에서 펌프될 뿐

구성 요소는 NOHTree(노드 계층 트리), PropertyGrid(리플렉션 기반 편집기), SceneViewPanel(D3D 뷰포트 임베드), CommandConsole(즉시 스크립팅), TerrainEditTool(raise/lower/smooth 브러시)이다.

가장 좋은 아이디어

플러그인 디렉터리 이름이 곧 노드 타입 이름이다. plugins/TerrainNode/, plugins/RpBase/, plugins/AbstractShaderNode/, plugins/TimeServer/ — 어떤 노드를 선택하면 에디터가 그 타입 이름으로 디렉터리를 찾아 initialize(parent, obj)를 호출하고, 전용 패널을 도킹한다. C++에서 새 노드 타입을 만들고 폴더 하나를 더하면 전용 툴이 생긴다. 등록부도, 스위치문도 없다.

/defects

되살린다면

순서가 중요하다. 앞의 셋을 통과하기 전에는 아무것도 컴파일되지 않으므로 나머지를 논할 수 없다.

  1. 컴파일 진입. type_id를 uintptr_t(또는 타입별 정적 카운터)로, #define override virtual 제거, hash_map → unordered_map, define.h:49 오타 수정. 여기까지가 x64 빌드의 최소 조건이다.
  2. CMake 도입 + Boost 외부화. vendored Boost를 패키지 매니저나 서브모듈로 밀어내면 저장소가 10분의 1로 줄고, 그 시점에 리눅스/맥 빌드 시도가 처음으로 의미를 갖는다.
  3. 소스 UTF-8 전환. euc-kr 상태로는 어떤 현대 편집기·CI 로그도 신뢰할 수 없다. 기계적 일괄 변환이라 위험이 낮다.
  4. 테스트를 D3D에서 분리. core_test는 렌더러 없이 돌 수 있다. WinMain을 main으로 바꾸고 CI에 연결하면, 이후 모든 작업에 안전망이 생긴다.
  5. 새 렌더 백엔드. 인터페이스가 이미 순수 가상으로 분리돼 있어 오히려 쉬운 축이다. 위 네 단계를 먼저 끝내야 착수 가치가 있다.
  6. 메서드 바인딩 현대화. 여유가 생기면 프로토타입 문자열 + 썽크 63개를 가변 템플릿 bind(&Node::setName)으로 대체한다. 코어 코드가 눈에 띄게 줄고 타입 검증이 생긴다.
/verdict

총평

설계 감각은 지금 봐도 좋다. 리플렉션 코어 하나에서 직렬화·스크립팅·에디터 UI를 파생시키는 구조는 2009년 개인 프로젝트 기준으로 상당히 야심적이고, 실제로 관철됐다. 씬 포맷을 따로 정의하지 않는다는 점, 스크립트 바인딩 코드가 클래스당 0줄이라는 점, 플러그인을 타입 이름으로 잡는다는 점 — 셋 다 같은 하나의 결정에서 나온 결과다. 렌더러 인터페이스와 DX9 구현의 분리도 제대로 되어 있다.

다만 실행 가능한 코드로서는 화석이다. D3D9 + MSVC 2010 + vendored Boost + euc-kr + #define override virtual + x86 전용 type_id 조합은 현대 툴체인에서 한 줄도 컴파일되지 않는다. 문서 폴더에 쌓인 2006–2008년 그래픽스 논문들(VSM, Parallax Occlusion, HL2 Shading, TF2 NPAR, Chunked LOD)이 이 프로젝트가 무엇을 향하고 있었는지 보여 주지만, 그 목적지에 도달하기 전에 멈췄다.

결론적으로 실용 엔진보다 학습 자료로서의 가치가 크다. "리플렉션 코어에서 툴을 자동 생성한다"는 아이디어를 실물로 확인하려는 목적이라면, 아래 네 파일만 읽어도 핵심이 전달된다:
